This is a deployment proposal. These files have not been installed or started on the VM.

`investment-backfill.py` invokes the existing, reviewed `prepare_live_rows.py apply` using the research service account and `/etc/research-backend.env`. The child enforces `INVESTMENT_APP`, verifies the complete source bundle, and takes the same `row-import-investment.lock` as the monthly worker. It retains committed row batches and the 12 GiB capacity ceiling. The fixed invocation uses `--max-rows 9100000 --batch-size 500 --retries 0 --month-pause-seconds 1`.

The wrapper also requires `--snapshot-id`. The prepared unit pins `pipeline-state` to `8f1ff2d04a4b4c31b31f0d470fc27894`, the source used for this initial bundle. It forwards `--source-snapshot-name pipeline-state --source-snapshot-id 8f1ff2d04a4b4c31b31f0d470fc27894` to the importer. Investment `apply` rejects an absent or invalid pair. Each month checks the source before loading and again locks that exact source head inside the same transaction that publishes the dataset head. If a new source snapshot wins first, publication raises `Conflict`, leaves the current dataset head intact, and the scheduler stops for attention. The scheduler state and successful reports are bound to both the manifest hash and source snapshot id. Never substitute the latest id on an old bundle to bypass this guard; prepare a verified bundle from the new snapshot instead.

The template requires the absolute installed importer path, the existing investment bundle's manifest path, and the locally verified SHA-256 of that manifest. Replace `@IMPORT_SCRIPT@`, `@MANIFEST@`, and `@MANIFEST_SHA256@` before installing the template as `research-investment-backfill.service`. Use the existing `/opt/research-backend/.venv`; no new package, scheduler account, database privilege, or paid resource is required. Both this unit and the monthly worker must read the same `BACKEND_DATA_DIR` setting.

The proposed timer waits 15 minutes after timer activation (including at boot) and at least 15 minutes after an unsuccessful service exit. These timer semantics and the successful `RemainAfterExit` behavior follow the [systemd timer documentation](https://raw.githubusercontent.com/systemd/systemd/main/man/systemd.timer.xml). The wrapper additionally persists a 900-second cooldown, so an early manual invocation cannot bypass it. Inner importer retries are disabled to avoid its normal 30-second retry interval. Each attempt writes its own bounded report under `/var/lib/research-backend/backfill`; the wrapper emits only a small status/error-code summary and discards raw child stdout/stderr. The existing collector and API remain unchanged.

Successful completion requires every manifest partition, the exact declared row counts, `queries_verified=true`, and the matching pinned source id in the report. It writes `investment-complete.json`; `RemainAfterExit=yes` and the unit's marker condition prevent another import. A wrapper interruption after a successful child report is recoverable. Non-retryable failures, including a superseded source, stop with `investment-needs-attention.json`. Transient failures stop after at most 96 attempts (roughly 24 hours of 15-minute cooldowns, plus execution time). Inspect the result before deliberately resetting any scheduler state. Do not delete import rows to restart it.

The proposed review/install sequence is: confirm the bundle hash and all three template values; check the non-root research account can read the importer, bundle, app environment, and wallets; render and validate both units with `systemd-analyze verify`; install the wrapper and units; then, only if this proposal is accepted, run `systemctl daemon-reload` and `systemctl enable --now research-investment-backfill.timer`. Enabling only the timer schedules the first attempt after 15 minutes; an immediate deliberate attempt uses `systemctl start research-investment-backfill.service` only after any previous manual import's 15-minute cooldown. Read `investment-state.json`, the latest `investment-attempt-NNN.json`, and the service journal for safe progress. `TimeoutStartSec=4h` bounds an individual process; successful 500-row commits survive interruption.

This backoff does not repair an exhausted UNDO tablespace. It leaves the initial load resumable while Oracle can reclaim space. Completion must not be reported until the complete marker and final partition counts exist. Existing raw files in object storage remain available throughout.

The reviewed index alternative remains a proposal only. The current primary key `(dataset_key, version_id, row_no)` is necessary for uniqueness and conflict detection during resume. Keep its index valid. Oracle documents making only the two nonunique secondary indexes unusable during a bulk load and rebuilding them afterward; this preserves their definitions and avoids their DML maintenance. An invisible index still receives DML maintenance and would not help. If an index were dropped instead, restoration would require `CREATE INDEX`, not `ALTER INDEX REBUILD`. Verify the actual constraint/index bindings and `SKIP_UNUSABLE_INDEXES` before considering any such DDL. [Oracle index guidance](https://docs.oracle.com/en/database/oracle/oracle-database/26/admin/managing-indexes.html)

Those two secondary indexes account for about 71% of the currently allocated observation-index bytes, but that is not a measured UNDO reduction. The primary-key index and metadata still generate work. Direct-path insert also appends above the high-water mark and takes exclusive write locks; keeping transactions small does not eliminate that allocation overhead. A simple extrapolation from the observed 1.63 million rows reserves about 3.74 GiB for rebuilding the two secondary indexes at 9.06 million rows, before temporary sort space and uncertainty. Thus a current 12 GiB check with the indexes absent would overstate available final capacity. Any trial would need serial rebuilds and a reserved recovery budget. Given existing UNDO exhaustion and uncertain benefit with the primary key retained, this alternative is not included in the proposed scheduler. [Oracle direct-path considerations](https://docs.oracle.com/en/database/oracle/oracle-database/26/admin/managing-tables.html)
